# 从零建设新系统

用于从零开发网站、Web App、管理系统或多页面产品。没有旧界面时，从用户任务和内容模型开始；不要求先提供截图或做旧页面问题审计。单个独立页面使用布局与风格路径即可，已有系统新增页面沿用其导航、组件和数据约定。

## 明确系统范围

从需求中识别用户角色、主要对象、核心任务、目标设备、必须交付的模块及已有技术条件。区分界面原型、可运行前端和需要连接真实服务的产品；后端、认证与存储按用户要求落实和验证，不能用界面效果替代。

用户指定的技术栈、功能范围和风格直接采用。检查空仓库或已有脚手架，沿用有效配置；未指定的常规选择根据需求合理推断并简述。仅对会改变实现方向、数据来源或权限边界的缺失信息提问，已授权自主选择时继续，不增加逐阶段审批。

## 先建立系统结构

用简短说明或必要的表格明确以下关系，可沿用项目现有记录，无需新增一套规划文档：

- **角色与任务：**谁操作什么对象、能做什么、从哪里进入；仅在需求涉及时设计登录、角色差异和权限反馈。
- **模块与页面：**每个页面的目的、主要内容、入口和下一步，区分列表、详情、创建或编辑、设置等实际需要的页面。
- **导航与路由：**全局导航、模块内导航、面包屑、返回路径及当前页面状态；菜单名称对应真实模块。
- **核心流程：**把页面连成能完成任务的路径，明确前置条件、操作结果、取消、失败恢复与完成后的去向。
- **数据与状态：**核心对象的标识、字段、状态及其变化由哪些操作触发；涉及接口时明确数据来源和边界。

例如物资管理的登记、台账、领用与归还应围绕同一物资对象连通；不为填满侧栏添加无关模块，也不默认把所有系统做成营销首页加数据看板。

## 建立共享界面规则

按[使用原则](usage-principles.md)推导产品气质、视觉重点与识别细节。已选风格在其范围内应用，未选风格且用户委托设计时自主选择；26 种风格提供表达参考，各页面结构按实际任务确定。

先实现可复用的导航与 App Shell、字体、语义 Token、布局尺度和基础控件。列表、详情、表单和反馈采用共同规则；不同页面可有不同信息密度与布局，但不各自发明一套 Button、Dialog 或错误处理。

复用已安装且合适的组件库，不因选风格就替换技术基础。需要复用指南时参考[设计系统输出](design-system-output.md)；规则可以落实在共享代码及项目现有约定中，不强制生成额外文档。框架元数据、favicon 与脚手架品牌清理见[新项目基础配置](new-project-shell.md)。

## 从完整流程扩展到全部范围

1. 先搭建可运行的路由和共享框架，明确导航入口及小屏收拢。
2. 选择能覆盖主要对象和操作的代表流程，例如列表 → 详情 → 编辑 → 保存返回，做通页面、数据变化及必要的校验和恢复。
3. 在允许范围内检查代表流程的布局、视觉和行为，再复用其组件与约定扩展到其余请求模块。代表流程是校准点，不是整套系统的交付终点。
4. 完成用户要求的页面与操作，消除死链接、无响应按钮、仅改变 Toast 而未更新对象的假操作，以及彼此孤立的演示页面。

共享对象应使用一致的标识和状态来源；创建、编辑或删除后，相关列表、详情与统计按任务约定同步。返回列表时按产品需要保留筛选和分页。共享状态不代表必须新增某个状态管理依赖。

原型允许使用自洽的模拟数据，并说明刷新或会话后的行为；要求持久化或真实接口时，应连接并验证对应能力。前端隐藏菜单不能证明服务端授权有效，本地模拟结果不能称为真实提交、支付或认证成功。

## 系统级收尾

在用户允许的测试范围内，选择代表性核心流程检查跨页面结果，结合源码与构建检查覆盖剩余范围；将未做的复杂交互验证列为简短人工验证项，不默认遍历全部页面或批量截图。

- 请求的模块、页面与操作实际存在，导航、返回及约定的深层路由访问可用。
- 同一对象在创建、详情、编辑、列表等相关位置的内容与状态一致。
- 共享组件、视觉 Token、术语与反馈一致；移动端能继续完成核心任务。
- 需求涉及的角色差异、空数据、接口失败、字段错误、提交中和成功状态有真实处理，未涉及的状态不为凑清单添加。
- 明确已实现与已验证的范围、模拟数据和真实服务的边界；不能以一个精致首屏或若干静态页面宣称整套系统完成。

新系统按交付范围与核心流程验收；已有界面的修改另按[工作流程](workflow.md)回看原问题。两者共享功能与视觉分开取证的原则。
